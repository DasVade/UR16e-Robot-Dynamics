# Python workflow and integrated planning-to-control results

Python is the primary runnable implementation. Original MATLAB/Simulink source
and repaired MATLAB routines live in [legacy](../legacy/README.md); shared URDF
and mesh assets remain at root `simulink/`. The [feature mapping](FEATURE_MAPPING.md)
distinguishes migrated functionality, replacements and unsupported modules.
No MATLAB/Simulink numerical equivalence is claimed.

## Interfaces and conventions

`Robot` exposes URDF mesh loading, FK, base-frame geometric Jacobian, bounded
numerical IK, mass matrix, positive gravity compensation, velocity-dependent
torque, inverse/forward dynamics and torque-driven simulation. Units are SI;
joint order is shoulder_pan/lift, elbow, wrist_1/2/3. Spatial vectors are
[linear;angular], in `base_link` (engine world), at tool0. For a wrench ON the
robot: `M*ddq + c + g = tau + J.T*w`. `inverse` subtracts J.T*w and `forward`
adds it. Independent energy-reference checks remain in `urdf_model.Model`.
The original UR `base` / `tool0` versus DH reconciliation remains as documented
in [the dynamics report](DYNAMICS_REPORT.md).

Numerical IK is a replacement for the original branch-based solver, not an
exact translation. The RRT and shortcut planner adapt the original joint-space
ideas while adding explicit limits, zero-distance guards and edge checking.
The old B-spline/time-optimization workflow is not claimed as ported: new
timing follows each validated straight joint-space edge with a rest-to-rest
quintic scalar, giving C2 position/velocity/acceleration through stopped knots.
This prevents interpolation from silently cutting across obstacles.

## Integrated experiment

Start q=[0,−1.2,1.2,−.8,.8,0], goal=[.9,−.5,.5,−.2,1.2,1]. A box with centre
[.635,.570,.482] m and half extents [.055,.055,.070] m blocks the direct joint
segment. A sphere at [−.25,.50,.30] m with radius .08 m is also checked and
rendered. These are the actual query geometries, not decorative obstacles.
Seeds 5170/5171/5172 all found detours; this is three small demonstrations,
not a broad reliability benchmark.

| Seed | Planning seconds | Raw length (rad) | Smoothed length (rad) | Direct edge valid |
|---|---:|---:|---:|---|
| 5170 | .133 | 2.6909 | 2.0082 | No |
| 5171 | .394 | 3.3605 | 2.2096 | No |
| 5172 | .116 | 2.7972 | 1.9635 | No |

Timing excludes smoothing and post-validation. Planning uses .04 rad Euclidean
joint-space spacing and a .015 m clearance margin; shortcuts use .01 rad and
final edges are rechecked at .005 rad. URDF position bounds constrain sampling.
Self-collision queries include indices 0…6 separated by at least 3; adjacent
and fixed helper pairs are excluded. This is a declared partial self-collision
policy, not a complete collision certificate.

The first seed's smoothed path is timed over **7.02 s**, quantizing segment
durations to .01 s so both integration grids use exactly the same reference.
Computed torque uses unchanged nominal gains 64/s² and 16/s, actual state
feedback, and clipped URDF effort bounds [330,330,150,56,56,56] Nm. Initial
offset is [.01,−.01,.01,−.005,.005,−.005] rad, with zero velocity. The plant
is integrated at .25 ms; contacts remain disabled and collision checking is
performed independently against query geometry. No contact response is used
to rescue an invalid trajectory.

Results:

- Pooled RMS over all joints and state samples: **0.00117913 rad**.
- Per-joint RMSE: [.00149190,.00149148,.00149129,.00074552,.00074588,.00074543] rad.
- Minimum clearance at 5 ms samples: reference **18.3486 mm**, actual **18.3486 mm**.
- Zero sampled collisions, invalid refined edges, position-limit violations,
  velocity-limit violations, applied-torque violations and saturation.
- Peak applied torque: 88.48 Nm (joint 2); per-joint values are in the JSON.
- Halving the step to .125 ms: identical desired state samples and maximum
  actual joint-state difference **7.13e−6 rad**.

Reference and actual simulated paths are checked separately every 5 ms, with
additional joint-space interpolation checks at <=.005 rad between samples.
Minimum reported clearance is over the 5 ms samples; refined edge checks are
reported separately. Limits are supplied-model bounds, not verified hardware
ratings. No continuous collision-safety or unmodeled-disturbance claim follows.

## Controller comparison and payload interpretation

The unified `compare` command reran the existing four cases and reproduced
their metrics exactly; no historical metric was replaced. The `payload`
command was also executed independently. Pooled nominal RMS is .008643 rad
for PD+gravity and .009635 for computed torque. With a 1 kg inertial payload
at tool0 and nominal controllers, these become .028008 and .186758 rad.
The addition has .001 kg m² diagonal inertia; visuals intentionally do not
invent a physical payload/gripper geometry.

Equations, gains and payload application were reviewed: CT uses the nominal
inverse model with actual q/v and desired acceleration plus acceleration-space
feedback; PD uses torque-space gains and nominal gravity. The two objectives
and gain units differ. The observed payload sensitivity is supported by saved
results and reproduced commands; a universal explanation or ranking of CT
against PD is not established. No tuning was performed to make a controller
win. Per-joint error/torque figures and full-precision metrics remain in the
[earlier report](DYNAMICS_REPORT.md). That report also retains the 1 ms numerical
instability and convergence evidence for the original comparison.

## Demonstrations

- `planning.mp4` / `.gif`: **kinematic playback** of the validated timed RRT
  path, with actual mesh obstacles, start/goal and end-effector trail.
- `execution.mp4` / `.gif`: mesh rendering at **torque-driven dynamic states**
  from the integrated execution, with desired and actual end-effector paths.
- `comparison.mp4`: original synchronized PD/CT torque-driven comparison.
- `payload.mp4` / `.gif`: synchronized CT nominal versus unmodeled-payload
  simulated states, identical camera/scale/clock. No visual error amplification.

These are distinct experiments; the 6 s nominal comparison does not contain
obstacles. Renderers use saved configurations only, and ffmpeg H.264 encoding
preserves the sampled 10 fps playback. Videos use explicit controls and posters
on the website with no autoplay or eager loading of every video.

## Simple commands

Linux/WSL Python 3.11; pinned numerical/mesh packages plus system **ffmpeg** for
MP4 export. No new distribution or paid compute is needed. This machine uses
`/home/yxlewis/.venvs/ur16e/bin/python`; on another machine:

```bash
python3.11 -m venv .venv
.venv/bin/python -m pip install -r portfolio/requirements-dynamics.txt
PY=.venv/bin/python
$PY portfolio/cli.py kinematics --output outputs/my_kinematics
$PY portfolio/cli.py compare --output outputs/my_comparison
$PY portfolio/cli.py payload --output outputs/my_payload
$PY portfolio/cli.py plan-track --output outputs/my_plan
$PY portfolio/cli.py plan-track --output outputs/my_plan_half --dt .000125
$PY portfolio/cli.py visualize --run outputs/my_plan
$PY portfolio/cli.py verify --run outputs/my_comparison
$PY portfolio/render_payload.py --run outputs/my_comparison
```

Choose fresh output folders. Reproduction exports intentionally refresh curated
figures in docs/migration. To independently compare integrated timesteps:
load the two `execution.npz` files, check equal `time`/`desired` against every
second half-step sample, then compare `q`. The committed convergence record
was computed that way. `cli visualize` generates planning/execution GIF, MP4,
posters, numerical review traces and tracking plots. `export_experiments.py`
continues to provide the original nominal/payload per-joint plots.

## Boundaries

Original group: **Yixiao Liu, Yusen Wu and Huaqian Zhao**. Python integration,
numerical checks and rendering are later extensions using established methods.
Symbolic derivation, exact analytic IK branch behavior, original time-optimal
B-splines, and robust/noise Simulink blocks remain legacy/unsupported; they are
not silently presented as migrated. MATLAB/Simulink remains unexecuted. Inertial
data are supplied model parameters, not experimentally identified manufacturer
truth. Discrete collision checking, one model/trajectory and three seeds cannot
establish physical robot safety, hardware accuracy or broad robustness.
